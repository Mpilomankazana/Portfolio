Robot World - Multiplayer Server-Client Combat & Exploration Game
The networked multiplayer server-client system this whole project is built around, an arena where multiple robots, each controlled by a separate client, move around a shared grid world and interact with each other and the environment.
How It Works
  1. The server is a standalone Java console program. It builds a configurable-size grid world scattered with obstacles, mountains, lakes, pits, and mines, and listens on a network port, managing all game state and enforcing the rules.
  2. Clients (a terminal version and a JavaFX GUI version) connect over TCP, each controlling one robot. A client starts with no knowledge of the world, it only learns about obstacles, edges, and other robots as its robot moves and uses the look command to scan its surroundings.
  3. Communication runs on a custom JSON protocol over sockets: the client sends a command (launch, forward, fire, mine, etc.), the server updates world state and responds with JSON describing what happened.
  4. Robots come in different "makes", Sniper, Tank, Scout, Demolisher, each trading off range, shields, and ammo differently, so no single make is strictly best.
  5. The server can save and restore a world's layout (size + obstacles) to a SQLite database, so a specific arena setup can be recreated later.
⚡ Brownfield Challenge The real point of the project: inheriting a minimal 2-commit starter version of this system and building it out, adding the persistence layer, the JavaFX GUI client, the console command system, mines, an HTTP API, and a full test/CI setup, while using CodeScene to keep the growing codebase clean along the way.

PortfolioPulse - Automated Multi-Manager ETL & Portfolio Analytics Infrastructure
A data engineering platform that transforms fragmented multi-manager financial feeds into a structured, queryable foundation for investment analytics. Modeled on real-world operational challenges from 27four Investment Managers, it eliminates the manual spreadsheet aggregation that historically consumed the majority of analysts' time.
Core Problem
Investment firms manage capital across dozens of external fund managers, each using distinct schemas, spreadsheet formats, and asset classes. Manual aggregation is error-prone, outlier prices, missing daily figures, and duplicate holdings corrupt portfolio valuations, and analysts spend up to 80% of their time cleaning raw data instead of performing return and risk attribution.
Architecture
  1. Ingestion: automatically pulls daily market prices and CSV fund allocations from external managers.
  2. Transformation: Pandas-based cleaning, schema standardisation, and OHLCV data validation.
  3. Relational load: normalised data persisted into PostgreSQL 16 via SQLAlchemy, with a domain-driven model covering fund managers, multi-asset allocation, and time-series prices.
  4. Orchestration: scheduled, headless execution in containerised Docker environments for reproducible runs.
⚡ Advanced Challenge Building a domain model expressive enough to link portfolios to multiple asset classes (equities, fixed income, cash), track holding weights against benchmarks, and support high-frequency market updates, while keeping the schema ACID-compliant and query-efficient for daily manager performance ranking and time-series valuation.

SiyaPhambili ("We Move Forward") - Civic Innovation Bridge Platform
A secure civic innovation bridge platform connecting hackathon prototypes, student projects, and local tech solutions with universities, tech hubs, and government entities for real-world deployment. Built under the "Build for Use" theme for the Geekulcha Annual Hackathon 2026 (#GKHack26) to bypass lengthy procurement cycles while maintaining strict data privacy, accountability, and security standards.
Core Pillars
  1. Two-Tier POPIA Data Gateway - splits project information into Tier 1 (Public: name, sector, description, stage, tech stack) and Tier 2 (Private & Consent-Gated: contact info, repo source, team identifiers), with access requiring explicit, audit-logged consent.
  2. Immutable Audit Trail - an append-only architecture where updates, deletes, and state changes are revoked at the database level; every access request generates a permanent log entry stamped with actor IDs, SHA-256 hashes, and timestamps.
  3. 5-Gate Accountability Pipeline - tracks projects through structured milestones (Idea → Prototype → Pilot → Scale → Implemented) to verify viability before public sector deployment.
  4. Role-Based Access Control - enforces strict permissions across four user perspectives: Public Viewers, Hackathon Builders/Teams, Verified University/Tech Hubs, and Government Officials.
⚡ Advanced Challenge Designing a POPIA-compliant, append-only data model that can prove, not just claim, that no record was ever silently altered, while still giving four very different stakeholder roles (public viewers, teams, institutions, government) the right slice of data at the right consent level.
